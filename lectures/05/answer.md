- 今回の用途に採用したい方式と、その理由・比較条件の限界：
採用したい方式：ベクトル検索（基本RAG）（複数ページにまたがる質問が多い用途なら Graph）。
理由：ベクトル検索は入力トークン数（3,027 tokens）と生成API推定費用（$0.001351）が最も小さく、全文投入（117,025 tokens / $0.035675）と比べてトークン数を約 1/39、費用を約 1/26 に抑えつつ正答と適切な引用を得られたため。Graph も費用を $0.002294 に抑えつつ 4.15 秒で応答し、前後ページや関連用語もたどれるため、発展的な質問への拡張性が高い。
比較条件の限界：
全文投入（全9資料・438ページ）と他3方式（第1〜3回本講義・214ページ）で対象範囲がそろっていない。   
単一ページで完結する質問1問・各1回の計測であり、複数ページをまたぐ質問や資料に答えがない質問での精度差を評価できていない。   
推定費用にはクエリ埋め込みや事前索引構築のコストが含まれていない。
- 気づき・疑問：
応答回数と速度・コストの違い：全文投入は入力が約 11.7 万トークンと膨大でもモデル応答が 1 回で済むため最速（3.51 秒）だったが、費用はベクトル検索の約 26 倍かかった。逆に Tree は目次を4段階でたどるためモデル応答が 5 回となり最長（11.49 秒）だったものの、ピンポイントで p.52 の本文だけを取得できており探索経路の透明性が高かった。
API の混雑によるばらつき：Graph の実行時には 503 エラー（モデル混雑）が 3 回連続で発生したあと 4 回目で成功した。また、同じモデル応答 2 回でありながら入力トークンが多い Graph（4.15 秒・5,773 tokens）の方がベクトル検索（7.13 秒・3,027 tokens）より速く終わっており、応答時間は API 側の負荷に大きく左右されるため複数回計測が必要だと感じた。
